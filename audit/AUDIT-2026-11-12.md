## 2. F-1（中）：`totalOwed` 是「按结算边界 floor 的累加」，用户应发是「跨边界一次性 floor」

### 机制

```solidity
// _updateReward，StakingRewards.sol:216
totalOwed += (supply * delta) / PRECISION;      // 每个结算边界 floor 一次，累加
```

```solidity
// _rewardOf，:521
(balanceOf[account] * (rpt - userRewardPerTokenPaid[account])) / PRECISION + rewards[account]
// 用户从上次结算到现在的整段区间，只 floor 一次
```

`floor` 是次可加的：`Σ floor(xᵢ) ≤ floor(Σxᵢ)`。一个没被结算的用户横跨 n 个全局结算点，
他的应发可以比 `totalOwed` 里记下的**多出 n-1 wei**。于是：

```solidity
// getReward，:357
totalOwed -= reward;    // reward > totalOwed 时 panic 0x11
```

`StakingRewardsETH.sol:248` 同款，`StakingRewardsV2.sol:139`（`totalOwed -= forfeited`）同款。

### 复现数字（按合约原式逐位模拟，非估算）

常数供给、常数速率下，两次间隔 1 秒的全局结算之后：

| `supply` (wei) | `rewardRate` (wei/s) | 结算 2 次差额 | 结算 10 次 | 结算 100 次 |
|---|---|---|---|---|
| `1000000000000000001` | `1e18` | **1 wei** | 9 | 99 |
| `1234567890123456789` | `604800` | **1 wei** | 9 | 99 |
| `1234567890123456789` | `1e18` | **1 wei** | 5 | 57 |

差额是正的，且**单调不减**——一旦越过 1 wei，这个用户就再也领不出来（每次新的结算让两边同速增长，
差额只会更大）。

> 编写窗口在 `FINDINGS §3.21` 的注释和 `Invariants.t.sol:184` 里已经记过这个现象（「两次 floor 之和
> 可能少 1 wei」），当时的判断是「未构造出完整可达路径」。**本文件补的就是那条路径**，
> 以及它不止 1 wei、并且连 `exit()` / `emergencyWithdraw()` 一起打掉。

### 最小链上复现形状（供编写窗口写成用例）

关键点：**供给不变、速率不变、用户 A 在两次全局结算之间不动作**。三个条件都能满足：

1. A 质押，之后不再调用任何函数；
2. 两个**没有任何仓位**的地址各调一次 `getReward()` —— 它们 `_updateReward` 走完、`reward == 0` 直接
   return，效果是「把池子结算两次」而不改 `totalSupply`、不改 `rewardRate`；
3. 两次之间 `vm.warp(+1)`，然后 A 调 `getReward()`。

断言不要写死 1 wei，让用例自己找状态：

```solidity
assertGt(staking.earned(alice), staking.totalOwed(), "deficit state reached");
staking.getReward();        // 修之前：panic 0x11；修之后：正常发放
```

若基座里已经有 1 wei 种子仓位，调整 A 的质押尾数（试 `1e18+1`、`1e18+3`、`1e18+7`）直到
`earned(alice) > totalOwed()` 成立——这条不等式的成立只取决于 `supply · Δ / PRECISION` 有没有余数，
换尾数一定能撞上。

### 影响

| 路径 | 后果 |
|---|---|
| `getReward()` | 永久 revert，奖励领不出来 |
| `exit()` | **整笔回滚**，连里面的 `requestUnstake` 都建不起来（本金还没被锁，但要分两步手动做） |
| V2 `emergencyWithdraw()` | **紧急出口本身失效**——这是最严重的一处，它存在的唯一目的就是「任何情况下都能拿回本金」 |
| 本金 | 未受影响，`requestUnstake` / `withdraw` 正常 |

所以等级是中不是高：钱不丢，但**承诺的退出路径会失效**，且只影响奖励。

### 为什么 250 条测试一条都没红

`test/StakingRewards/Invariants.t.sol:184-198` 的注释已经把这个现象写清楚了，然后用
`ROUNDING_DUST = 1e6` 的容差放过了：

```solidity
assertLe(booked, owed + ROUNDING_DUST, "booked rewards <= liability (+ dust)");
```

**测试承认了它，合约侧却没有夹逼。** 加上 handler 里所有调用都是 `try/catch {}`（`:90` 等），
一次「本该成功却 revert」的领奖会被吞成 no-op，序列照常继续。这条缺陷在现有证据体系里是隐形的。

### 修法（三处，形态一致）

```solidity
uint256 owed = totalOwed;
totalOwed = reward >= owed ? 0 : owed - reward;
```

`emergencyWithdraw` 里对 `forfeited` 同样处理。`>=` 而不是 `>`：差额已经被 floor 吃掉，
这时把负债清零比留 1 wei 残值更接近事实。

### 验收标准

1. 新增用例在**未修**的实现上必须红，且红因是 `panic: arithmetic underflow`，不是断言失败；
2. 修完后该用例全绿，且 `test_GetRewardClearsLiability`、`test_EmergencyWithdrawIgnoresCooldown`
   等相邻用例保持绿（判据仍然是「定向」）；
3. `invariant_RewardLiabilityWithinBalance` 的容差可以保留（它守的是另一个方向），
   但要在注释里改成「差额存在，合约侧已夹逼，此处容差只用于不变量自身」——**不要再让容差承担
   「绕过已知缺陷」的角色**。

## 3. F-2（中）：「V2 吃掉 95% 部署预算」是错的

### 实测

| 版本 | runtime | README 声称部署 gas | **实测部署 gas** | 理论值（200 gas/B deposit） |
|---|---|---|---|---|
| V1 | 9,247 B | 14,662,000 | **2,101,403** | 1,849,400 + 220k 开销 |
| V2 | 10,243 B | 16,212,000 | **2,316,869** | 2,048,600 + 220k 开销 |

实测值与理论值吻合到 3% 以内；README 那两列高 7.0 倍。

链上旧实例的回执也对不上：`0xB39a…` 的 runtime 只有 **6,325 B**（deposit 1.27M），
回执却记了 **10,885,170** gas。两个数字不可能同时是「标准 EVM 计价下的实际消耗」，
所以那两列的基数取自 gasLimit / 估算值，不是 `gasUsed`。

### 影响

README 由此得出两条结论，都失去依据：

- 「部署 V2 时 `--gas-limit` 要给 16,700,000 以上，给 16,000,000 会 OOG」→ 实际 2.3M 就够，
  给 16M 只是浪费，不会 OOG；
- 「**V3 之前必须先瘦身**，只剩约 369 字节」→ 真实余量约 **14.4M gas（85%）**、
  代码体积 10,243 / 24,576 B（还剩 14KB）。

按错数去拆 view 合约、降 `optimizer_runs`，是在为一个不存在的约束付代价。

### 验收标准

用一次真实部署（Sepolia 或 anvil 都行）重新取 `gasUsed`，把表格两列和「硬约束」小节的结论一起改。
改完在 `FINDINGS.md §7.2` 的「无 gas 基准」那条后面补一句实测值，免得下次又漂回去。

## 4. F-3（低）：角色分层在 ADMIN 这一层是断的

`StakingRewards.sol:62-66` 的注释和 README 都写明了这个性质，**但部署形态给了错误的安全感**：
`set-env.ps1` 把 ADMIN 与 UPGRADER 交给两个不同 EOA，读起来像「UPGRADER 上了时间锁就守住了升级」。

实际上 ADMIN 被攻破 = `grantRole(UPGRADER_ROLE, self)` + `upgradeToAndCall` 换实现 → 转走全部本金，
**UPGRADER 上的时间锁/多签完全不起作用**。`test_ManagerAndGuardianCannotUpgrade` 钉住的是
MANAGER/GUARDIAN，管不到这一层。

部署前必须定的一件事：ADMIN 放进同一个时间锁，或者在 `initialize` 里
`_setRoleAdmin(UPGRADER_ROLE, UPGRADER_ROLE)`（代价是 UPGRADER 全丢就永久锁死升级）。
保持现状也可以，但 README 要写成「ADMIN 等价于超级权限，不是日常治理权」。

## 5. F-4（低）与 F-5（低）

**F-4 `exit()` 反向锁人。** `:320-326` 合并挂起请求时取最晚解锁时间，`:368-373` 的 `exit()` 会
以当前余额再挂一笔。用户先挂 100（已过冷却、随时可提），再点 `exit()` 退剩下的 50 —— 那 100
重新等满 24 小时。名字叫 exit，行为是「再多锁一天」。
最低成本处理：README 里写成「先 `withdraw()` 再 `exit()`」；要根治得把单槽改数组（`V2` 注释里已列为
单独一次升级）。

**F-5 ETH 池无 `emergencyWithdraw`。** `FINDINGS §6.1` 挂着等拍板，我的结论是**该加**：
V2 花一整个功能兑现「本金不该被任何一方的设定冻住」，ETH 池冷却上限 30 天却没有出口；
而且它不可升级，V2 修不到它。这个洞不会自己消失。

## 7. 核对过、确认没有问题的部分（不要再动）

| 项 | 结论 |
|---|---|
| 存储布局 | `forge inspect` 逐槽对比 V1/V2 完全一致：16 槽 + `__gap[34]`，`claimPaused` 在 slot 15，gap 从 16 起。OZ 5.7 的 `ReentrancyGuard` 确实已改命名空间存储，没多吃 slot 0，README 那句话是对的 |
| CEI | `withdraw` 先 `delete pendingUnstake` 再转账；`getReward` 先 `rewards[msg.sender] = 0` 再转账；ETH 版先清状态再 `call` |
| 重入 | 所有动钱入口都挂了 `nonReentrant`；`exit()` 自身不持锁但两次内部调用各自持锁，重入会被挡 |
| 权限 | 四个治理函数的 `onlyRole` 无一遗漏；`_authorizeUpgrade` 有实现且有角色 |
| `recoverETH` 上限 | `balance − totalSupply − totalPending` 算对了三种钱（计息本金 / 冷却本金 / 误转） |
| 两级闸门 | `pause` 只挂 `stake`，`pauseClaim` 只挂 `getReward`，本金路径没被任何闸门碰到 |
| 升级保状态 | V2 零新增变量，`__gap` 未动，`reclaim` 语义与 V1 一致 |
